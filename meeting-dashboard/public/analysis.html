Cal.com: analysis and dashboard integration

Researched 11 November 2026 · MeetingSchedule project · Official Cal.com documentation

Cal.com can serve as the scheduling engine behind a remotely accessible dashboard. Its REST API supports the core meeting lifecycle and personal scheduling configuration. Reproducing every Cal.com website action is a substantially larger product: provider authorization, billing, team administration, payments, routing, and enterprise controls need their own integrations and permissions. This delivery implements the core scheduling workspace and documents the remaining scope explicitly.

Authentication update: Google Identity Services sign-up is now implemented alongside the existing Sites sign-in. Activation requires a registered GOOGLE_CLIENT_ID and a public Site audience. See the project’s Google sign-in setup guide. The scheduling integration still uses each person’s own Cal.com credential.

1. Product and domain model

Cal.com combines booking pages, availability calculations, calendar synchronization, conferencing, team scheduling, routing, and notification workflows. A host defines how people can meet; a booker chooses an available slot; Cal.com creates a booking and coordinates its downstream effects. The dashboard delegates those calculations and integrations to Cal.com instead of duplicating its scheduling engine. Product overview.

  • Account: identity, timezone, API permissions, connected applications, and account entitlements.
  • Event type: a reusable meeting definition, including duration, slug, location, booking questions, schedule association, notice periods, buffers, and limits.
  • Schedule: recurring working hours in a named timezone, with date-specific overrides. An event can use a particular schedule or the host's default.
  • Slot: a candidate start time returned for an event and query range. A slot is not a confirmed reservation.
  • Booking: the resulting meeting, attendees, host, status, start/end times, location, and opaque booking UID.
  • Teams and organizations: additional ownership and permission layers. Collective and round-robin meeting types have host-selection behavior beyond individual meetings.

These resources remain in Cal.com. There is no second scheduling database in this project. Refreshing the dashboard reloads authoritative records; local UI state is temporary. Event types, schedules, bookings.

3. API contract verified for this implementation

Base URL: https://api.cal.com/v2. Credentials use Authorization: Bearer …. Version headers are pinned per resource and operation rather than assigning one global date. The documentation changed beyond older 2024 examples; in particular, the current booking list uses cursor pagination.

Booking lists accept one status per request. The UI follows pagination.nextCursor when hasMore is true, and labels metrics as calculated from the loaded records. Search and calendar filtering operate on those loaded records; they are not global account analytics. Booking pagination and filters.

A meeting can be identified by event-type ID or by an event slug plus a personal username or team slug, with an organization slug when appropriate. The slot request includes a UTC range; the dashboard filters the returned instants to the selected local date. Booking creation sends the exact selected instant converted to UTC and includes the attendee's IANA timezone. Cal.com performs the final availability check. Available slots.

Booking lifecycle operations use the opaque UID. Rescheduling sends a new start and optional reason; cancellation and decline collect a reason in a confirmation dialog. These writes may send notifications. A network timeout does not prove a write failed, so the UI advises refreshing before trying again and the gateway does not automatically retry writes. Rescheduling, cancellation, confirmation, decline.

5. Security and data flow

Browser → same-origin API gateway → Cal.com API v2 → connected calendars and workflows. The application uses Sites' authenticated identity headers as the host-enforced boundary. API routes reject missing identity. Cal.com credentials determine which scheduling resources that user may access; an arbitrary resource ID never grants additional permission.

  • The API key is submitted once over HTTPS and verified. It is never baked into a client bundle, saved to localStorage, or written to the repository.
  • An AES-GCM encrypted cookie contains the credential, platform user ID, and eight-hour expiry. It is Secure, HttpOnly, SameSite=Strict, and scoped with the __Host- prefix.
  • The encryption secret is a protected hosting environment variable named CAL_SESSION_SECRET. Each request validates user binding and expiration before forwarding.
  • Mutations require a matching Origin. Only explicit scheduling paths and methods are permitted. The upstream host is fixed, redirects are rejected, and responses are marked no-store.
  • Bypass flags for calendar conflicts, out-of-bounds booking, and booking limits are stripped.
  • Credentials and booking responses are not logged by application code. Booking UIDs should be handled as sensitive capability-like identifiers, consistent with Cal.com's FAQ.
  • Disconnect clears the browser cookie. It does not revoke the underlying Cal.com key. A copied session cookie remains valid until expiration unless the credential or encryption secret is revoked/rotated.

The current design deliberately avoids a shared organization-wide API key. For a future multi-tenant release, use registered OAuth clients, scoped access/refresh tokens in durable encrypted storage, explicit membership policies, refresh/revocation flows, and audit events without secrets. 6. Operations and reliability

The frontend is React on the supplied Vinext/Sites runtime. The Cal.com gateway is intercepted in the Cloudflare Worker before framework routing. Hosting provides HTTPS and authenticated private remote access. No database is required for this version; Cal.com is the durable system of record. The default displayed timezone is Asia/Yakutsk, as supplied by the client's time context, and users can change it.

Cal.com documents a default API-key rate limit of 120 requests per minute. The gateway surfaces 429 and Retry-After, sets upstream timeouts, and avoids automatic booking retries. Large shared deployments need additional rate limiting, observability, and an agreed Cal.com usage allowance. Availability results can change between query and submission; final API errors must remain visible. Rate limits.

To operate: deploy the application; configure the hosting session secret; sign in; enter an existing Cal.com key through the Connection form; verify your profile, events, and availability; then book from the dashboard. New calendar integrations, billing changes, and API-key provisioning may still require an external authorization flow.

7. Verification and acceptance

Automated gateway tests cover identity enforcement, origin protection, encrypted-session tampering and expiry, cross-user isolation, credential verification, route restrictions, booking-limit protection, pagination forwarding, rate-limit handling, ambiguous network failures, and disconnect. Type checking and production compilation validate application structure. Browser checks use synthetic API responses to exercise workflows without creating real meetings or notifying people.

Live integration limitation: no user Cal.com key was provided in this task. Real-account reads and booking mutations cannot be verified until a user connects. Local and mocked tests are not evidence of successful real-world calendar delivery. Deployment status is checked separately from Cal.com integration readiness.

Recommended acceptance after connection: create a disposable event type and schedule; check availability in two timezones across a daylight-saving transition; book a consenting test attendee; confirm the calendar invitation; reschedule and cancel; test a required-question event; verify an expired key and 429 response; and confirm intended viewer access. Do not claim paid events, email verification, recurring series, or enterprise administration are supported until their specific flows are implemented and tested.
